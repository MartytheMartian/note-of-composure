# CLAUDE.md

## Commands

- `npm run dev` — start the Vite dev server (HMR)
- `npm run build` — `tsc -b && vite build`; this is the **only** command that exercises the strict type-checking settings (see Gotchas below) and generates the PWA manifest/service worker
- `npm run lint` — oxlint
- `npm run preview` — serve the production build locally, for verifying PWA/manifest behavior
- No test suite exists and none should be added unless explicitly requested — verification during development is done via disposable scratch scripts run with `npx tsx <file>.ts`, not a committed test framework
- Don't invoke the `/run` skill (or otherwise launch the dev server + drive a browser) to verify UI changes in this repo. Verify with `npm run build` and by reasoning about the change/CSS; let the user do their own visual check.

## Architecture

### Core concept / data flow

One relative (root-agnostic) JSON-shaped music library (`src/theory/data/musicLibrary.ts`) is derived into an absolute (rooted) instance on demand for whichever of the 12 roots is selected (`src/theory/absolute.ts`). A separate precomputed index (`src/theory/relationshipIndex.ts`) answers "which chords fit in this scale" / "which scales contain this chord" bidirectionally, and also "which chords/scales contain these notes" given an arbitrary pitch-class selection. Global app state holds `mode` (Relative/Absolute), `rootPitchClass`, and `listMode` (Scales/Chords/Notes/Progressions — which view the home route shows); which specific scale/chord is being viewed lives in the URL, not in state.

Relationship links (a diatonic chord shown on a scale page, or a scale shown on a chord page) are transpositions of the currently-selected root, not just a link to another relative chord/scale id. `scaleDetail.tsx`/`chordDetail.tsx` compute the correctly-offset root pitch class for the label already (translation-invariant relationships re-anchored to the selected root), but the `<Link>`'s `onClick` must *also* dispatch `SET_ROOT` with that same offset before navigating. Forgetting this is a real bug that shipped once: the link's label would correctly read e.g. "Eb major" for a diatonic chord of D Phrygian, but clicking it silently rendered "D major" instead, because the chord detail page has no idea it was reached via a scale's b2 degree — it just reads whatever root happens to be globally selected.

### `src/theory/` — framework-free core engine

- **notes.ts** — `LETTER_CYCLE`, `NATURAL_SEMITONES`, and `ROOTS` (the 12 chromatic roots; naturals get one spelling, the 5 black keys get two, sorted natural-then-sharp-then-flat so `ROOTS[pc].spellings[0]` is always the sensible default label). Also exports `chromaticIntervalLabel(offset)`, a fixed 12-entry lookup (`1, b2, 2, b3, 3, 4, b5, 5, b6, 6, b7, 7`) for labeling an arbitrary semitone offset in Relative mode when it isn't anchored to any scale's `degreeLetterSteps` — used by the Progressions builder, since a progression chord's root offset is freeform and has no scale degree to derive a letter-based label from (unlike `getRelativeScaleDegreeLabels`). `romanNumeralLabel(offset, isMinorQuality)` builds on `chromaticIntervalLabel` for the Progressions builder's roman-numeral chip label (e.g. "I", "ii", "bIII") — it reuses the same digit+accidental table and just converts the digit to a roman numeral and case-shifts it. `isMinorQuality` is the caller's job to compute; `progressionBuilder.tsx` passes `chordType.intervals[1] === 3`, since every chord type's `intervals` array is authored in stacking order (root, 3rd, ...) and checking all 30 entries in `chordTypes.ts` confirms that test exactly matches the minor/diminished/half-diminished family and nothing else — a deliberately simple heuristic that doesn't attempt a `°` suffix for diminished chords or fold in 7th/extension symbols (e.g. no "ii7"), since the goal is just the triad-level position in the key, not a full harmonic-analysis label.
- **spelling.ts** — `spellNote(root, letterSteps, semitonesFromRoot)` is the one load-bearing primitive: walks the letter cycle from the root and solves for the accidental that lands on the right pitch class (e.g. root F, 4th degree → B, solved accidental -1 → Bb, never A#). Throws if the accidental would exceed a double sharp/flat.
- **absolute.ts** — `getAbsoluteScale`/`getAbsoluteChord` turn a relative definition + root into spelled notes. Contains `spellSequenceWithFallback`/`candidateLetterStepPatterns`: a fallback letter-reassignment search that only kicks in when a scale's authored `degreeLetterSteps` produces an invalid accidental for a *specific* root. This is real, not defensive-only — testing all scale types × all 12 roots turned up Whole Tone rooted at A#/Bb producing an invalid spelling under the naive approach; the fallback searches alternate letter-to-degree assignments and picks whichever keeps accidentals smallest. Also exports `getRelativeScaleDegreeLabels` for degree display with no root (Relative mode).
- **harmonize.ts** — `diatonicHarmonization()` stacks thirds (degrees i, i+2, i+4[, i+6]) and matches the resulting shape against the tertian entries in `RELATIVE_CHORDS` to name each degree's chord. Only meaningful when a scale is flagged `supportsDiatonicHarmonization: true` (major/minor family + modes; pentatonic/blues/whole-tone/diminished/bebop are not).
- **subsetMatch.ts** — `toBitmask`/`isSubset`: 12-bit pitch-class bitmask subset check, the primitive behind every "does X fit inside Y" query.
- **relationshipIndex.ts** — precomputes every (scale type × 12 roots) and (chord type × 12 roots) bitmask once, module-level cached (`buildIndex()`, memoized via module-scope `scaleInstances`/`chordInstances`). **Relationships are translation-invariant**: `getChordsInScale`/`getScalesContainingChord` are always called with `rootPitchClass = 0`, and the returned offsets are re-anchored to the actually-selected root only at display time in the components. This is why `scaleDetail.tsx`/`chordDetail.tsx` never pass `state.rootPitchClass` into these lookups directly — doing so would be both unnecessary and wrong. `findScalesContainingNotes`/`findChordsContainingNotes` (added for the Notes feature, `components/notesFinder/notesFinder.tsx`) are the odd ones out in this file: they take a concrete, unrooted-but-absolute `PitchClass[]` selection directly (no root offset involved at all, since the input is already specific pitch classes, not a relative shape), bitmask it with `toBitmask`, and return every (type × root) instance where `isSubset(selectedMask, instance.mask)` — i.e. subset match, the type may contain more notes than were selected, not just exactly those notes.
- **sequence.ts** — `assignOctaves()` walks a chord/scale's pitch classes in their *authored* order (not numerically sorted) and assigns real octaves, bumping the octave whenever a tone doesn't climb above the previous one. This is what places a 9th/11th/13th correctly an octave above the root. Shared by the piano (visual) and `audioEngine` (playback).

### `src/theory/data/` — the relative library itself

- **scaleTypes.ts** — 4 parent 7-note patterns (major, harmonic minor, melodic minor, harmonic major) expanded into all 7 modes each via `deriveModes()` (rotates the interval array — avoids hand-typing ~28 variants), plus 8 hand-authored non-heptatonic scales (pentatonic ×2, blues, whole tone, diminished ×2, bebop ×2), each with an explicit `degreeLetterSteps` since they don't fit the "one letter per degree" default.
- **chordTypes.ts** — ~30 hand-authored chords. Interval arrays are listed in **stacking order** (root, 3rd, 5th, 7th, 9th, ...), *not* numeric-ascending order — e.g. add9 is `[0,4,7,2]`, not `[0,2,4,7]`. This is intentional and load-bearing for `sequence.ts`'s octave assignment; don't "fix" it into sorted order.
- **progressionTypes.ts** — `RELATIVE_PROGRESSIONS`, a small hand-authored library of named common progressions (Classic Cadence, Pop Progression, Axis Progression, Doo-Wop, Jazz Turnaround, Andalusian Cadence), each a `RelativeProgressionDefinition` (`theory/types.ts`) with `slots: ProgressionSlotDefinition[]` — a `{ chordId, rootOffset }` pair per chord, `rootOffset` being semitones from the progression's own root (i.e. the "I" chord in each preset has `rootOffset: 0`). Also exports `MIN_PROGRESSION_SLOTS`/`MAX_PROGRESSION_SLOTS` (1 and 12), the bounds the Progressions builder's add/remove buttons and `persistence.ts`'s load-time validation both check against. Presets are left at their natural length (mostly 4 chords) rather than padded/repeated to the max — the builder's slot count is dynamic, not fixed.
- `ScaleCategory`/`ChordCategory` (in `theory/types.ts`) and `AppMode`/`ListMode` (in `state/types.ts`) are `as const` objects + derived union types, **not TypeScript enums** — `tsconfig.app.json` has `erasableSyntaxOnly: true`, which forbids real enum syntax.
- `ScaleCategory`'s values are the literal display strings, not bare PascalCase (e.g. `MajorFamily: 'Major Family'`), so the list page can render a category name directly with no formatting step. `listPage.tsx`'s `spaceCategoryName()` helper predates this and is now a no-op for scales (its regex only inserts a space between an adjacent lowercase/uppercase pair, and there's already a space in the data) — it's still doing real work for nothing today; ChordCategory's values were always single words, so it was never doing anything for chords either. Harmless dead weight, not a bug, but don't be surprised it looks pointless.

### `src/state/` — React Context + `useReducer`

Mirrors the code style of the sibling project `C:\Users\William\Code\tiller\Web` (referenced in `design.md`): a bare `context.ts` (`createContext` only) split from `provider.tsx` (reducer/effects), anonymous `export default function (p: XProps) {}` components, direct `localStorage` calls with no wrapper library. `persistence.ts` uses one versioned localStorage key (`note-of-composure:v1`).

`AppState.progression` (a `ProgressionSlotDefinition[]`, length between `MIN_PROGRESSION_SLOTS` and `MAX_PROGRESSION_SLOTS` from `theory/data/progressionTypes.ts`) is the one user-configured chord progression, persisted like every other field. There's no separate "progression root" concept in state — the progression's own root ("I") is just whatever `state.rootPitchClass`/`state.mode` already is, the same Relative/Absolute duality every other page uses; each slot's `rootOffset` is added to that. `SET_PROGRESSION_SLOT` replaces one slot in place, `SET_PROGRESSION` replaces the whole array at once (used when loading a preset from `RELATIVE_PROGRESSIONS`), and `ADD_PROGRESSION_SLOT`/`REMOVE_PROGRESSION_SLOT` grow/shrink it — all four are no-ops in the reducer itself (not just disabled in the UI) at the `MIN_PROGRESSION_SLOTS`/`MAX_PROGRESSION_SLOTS` boundary, so the invariant holds even against a stale/hand-edited localStorage blob.

### Routing

`HashRouter`, not `BrowserRouter` — routes are `/scale/:scaleId`, `/chord/:chordId`, and `/`. Chosen so the installed PWA doesn't need server-side rewrite rules for a static host. The manifest's `start_url` is `/#/` to match; if routing is ever changed to `BrowserRouter`, the manifest must be updated too.

`/` renders `ListPage` (`components/listPage/listPage.tsx`) — there is no persistent sidebar; the Scales/Chords/Notes/Progressions view only ever exists as this one home-route page, switched on `state.listMode`. `App.tsx` restores `state.lastPath` on the very first mount only, guarded by a `useRef` flag on the top-level `App` component itself, not a child scoped to the `/` route. That distinction is load-bearing: a route-scoped guard remounts (and re-arms) every time you navigate back to `/`, which produced a real bug — picking a different list mode dispatches `SET_ROOT`/navigates to `/`, but `state.lastPath` hasn't caught up to the new URL yet on that render (it's set by a separate effect one tick later), so a route-scoped restore-check would immediately bounce you back to whatever page you'd just left. The top-level ref only ever fires once per app load, which is the only time restoring `lastPath` is actually wanted.

### Components

- **components/piano/piano.tsx** — builds a fixed 2-octave key layout (C4–B5, MIDI 60–83) once at module scope; highlighting comes from feeding the current notes through `assignOctaves()`. `pianoKey.tsx` is purely presentational. Active/root black keys additionally get a `1px solid var(--border-color)` outline (the same color used for the divider between white keys), so a highlighted black key stays visually distinct next to a highlighted white key instead of both just being blocks of the same accent color.
- **components/drilldown/scaleDetail.tsx & chordDetail.tsx** — the two content pages. Both show the Piano + a play button *only* when `mode === Absolute` (Relative mode has no concrete pitch to display or play) — this was a design assumption made during planning, not something explicitly confirmed by the user, so revisit it if it ever feels wrong. `chordDetail.tsx`'s `<h2>` shows the fully-qualified name (e.g. "C Minor"), not the short symbol; the symbol ("Cm") gets its own `Symbol:` line styled like the `Category:` line beneath it. `scaleDetail.tsx`'s diatonic-chords list shows only the chord link/label, with no `(triad)`/`(7th)` suffix — `r.isSeventhChord` is still computed but no longer rendered there. Both pages also bind a `window` `keydown` listener (in a `useEffect`, torn down on unmount) that plays the Notes list's `i`-th entry when the `i` digit key is pressed — `Number(e.key) - 1` indexed straight into `noteMidiNotes`, the same array the row's own `onClick={() => playNote(noteMidiNotes![i])}` already uses, so the shortcut and the click do exactly the same thing. Like the click handler, it's a no-op outside Absolute mode (`noteMidiNotes` is `undefined` in Relative mode, so the effect bails before attaching the listener). It ignores keydowns with a modifier held (so Ctrl+1-style browser shortcuts aren't hijacked) and keydowns targeting a `SELECT`/`INPUT`/`TEXTAREA` (so the page's own `SortOrderSelect` dropdown doesn't fight with global digit-key playback). There's no shared hook for this duplicated-in-both-files logic — same rationale as the rest of `src/state/`'s inline-`useContext` convention, avoiding a custom hook wrapper for ~10 lines already duplicated elsewhere between these two files (the Notes-list JSX itself).
- **components/rootSelector/rootSelector.tsx** — a single `<select>` that merges what used to be a separate Relative/Absolute button toggle plus a root-note picker into one control: a `'relative'` sentinel option alongside the 12 roots. Picking a root dispatches both `SET_MODE: Absolute` and `SET_ROOT`; picking "Relative" dispatches `SET_MODE: Relative` only, leaving `rootPitchClass` untouched. There is no `mode-toggle` markup anymore.
- **components/listModeSelector/listModeSelector.tsx** — the Scales/Chords/Notes/Progressions `<select>`, docked in the header to the right of the root selector. Changing it dispatches `SET_LIST_MODE` and also calls `navigate('/')`, since picking a mode should always jump to `ListPage` even when you're currently on a scale/chord detail page.
- **components/listPage/listPage.tsx** — renders at `/`. `state.listMode === ListMode.Notes` and `=== ListMode.Progressions` each short-circuit (to `<NotesFinder />`/`<ProgressionBuilder />`) before the rest of the component body runs, so the grouped-by-category rendering below is Scales/Chords-only and treats "not Scales" as "must be Chords" (a binary ternary, not an exhaustive branch) — safe only because both other modes already returned above it. If a 5th `ListMode` is ever added, it needs its own short-circuit in that same spot, or it will silently fall through and render as Chords. For Scales/Chords it groups `RELATIVE_SCALES`/`RELATIVE_CHORDS` by category and renders one chip-style list per group. Reuses the same chip `<ul>`/`<li>` styling as the detail pages — `.list-group` rides along in the same CSS selector list as `.scale-detail`/`.chord-detail` rather than duplicating those rules.
- **components/notesFinder/notesFinder.tsx** — the Notes view (rendered by `listPage.tsx`, not its own route). Its `<h2>` sits in a `.page-heading` row next to an `<InfoButton>` (same `common/infoButton/infoButton.tsx` used by `progressionBuilder.tsx`), with prose `<p>`s explaining the note picker, the 2-note minimum, and that results are clickable. A row of 12 toggle `<button>`s, one per `ROOTS[pitchClass]` (chromatic order, same as `rootSelector.tsx`), backed by local `useState<Set<PitchClass>>` — the selection is intentionally **not** persisted to `AppContext`/localStorage, so it resets every time the Notes view is (re)mounted. Below 2 selected notes, both the scales and chords sections show a "select at least two notes" message instead of a list (`relationshipIndex.ts`'s `findScalesContainingNotes`/`findChordsContainingNotes` aren't even called below that threshold). Results are subset matches — a match may contain more notes than were selected, not just exactly those — sorted by root pitch class first, then by the matched type's declaration-order index within `RELATIVE_SCALES`/`RELATIVE_CHORDS` (which already groups by family/category, so this reads as "sorted by root, then family" for free without a second explicit category sort). Labels are root+name concatenations (`"D Major"`, `"E Locrian"`), the same convention as the `<h2>` in `scaleDetail.tsx`/`chordDetail.tsx` — full `name`, never the chord `symbol`. Clicking a result's `<Link>` dispatches both `SET_MODE: Absolute` and `SET_ROOT` (mirroring `rootSelector.tsx` picking a root) *before* navigating, same "compute the offset once, dispatch it in `onClick`" shape as the diatonic relationship links described above — this one is unconditional (always forces Absolute) rather than gated on already being in Absolute mode, since every result here is inherently a concrete rooted pitch set, so there's no relative-mode-appropriate label to preserve.
- **components/common/infoButton/infoButton.tsx** — generic, content-agnostic trigger + explanation modal, meant to be reused across pages (currently only wired up on the Progressions page, via `progressionBuilder.tsx`'s `.page-heading` wrapper around its `<h2>`). The trigger is a plain italic "i" glyph in a circle (`.info-button`), not an icon asset/library glyph — consistent with the rest of the app never pulling in an icon set. Takes `title` + arbitrary `children` (expected to be prose `<p>`s, not lists — the Progressions content was deliberately rewritten from a nested `<ol>` to plain sentences) and renders a native `<dialog>` (`showModal()`/`close()`), not a hand-rolled overlay `<div>` — this gets Escape-to-close, focus trapping, and top-layer stacking (no z-index fighting with the sticky `.header`) for free. Backdrop-click-to-close is done via `e.target === e.currentTarget` in the dialog's own `onClick` (a click landing outside `.info-modal-content` hits the `<dialog>` box itself, since the `::backdrop` pseudo-element isn't a real clickable descendant). The `title` renders as a bare `<h3>` (no `.section-heading` row anymore — Close used to sit next to the title but was moved to its own bottom-right `.info-modal-actions` row instead), which needs the `.info-modal .info-modal-content h3` override in `styles.css` to zero its top margin: the generic `.detail-pane h3` rule (`margin: 1.5rem 0 0.5rem`) has equal specificity to `.section-heading h3`'s `margin: 0` and wins on source order, so a plain scoped-but-equal-specificity fix isn't enough — it needs the extra class to actually win. `.page-heading` (in `styles.css`) is the shared flex-row hook other pages should reuse to place an `<h2>` next to this button; its `h2` gets `line-height: 1` so the title's line box doesn't overhang the shorter button and throw off the row's vertical centering.
- **components/progressionBuilder/progressionBuilder.tsx** — the Progressions view (rendered by `listPage.tsx`, not its own route, same as `NotesFinder`). Renders `state.progression` as a row of chord chips — label is `{root}{symbol}` in Absolute mode, `{chromaticIntervalLabel(rootOffset)} {chord name}` in Relative mode, the same Absolute/Relative label split `chordDetail.tsx`/`scaleDetail.tsx` use for their relationship lists. Each chip also shows a second, muted line (`.chord-chip-degree`) with `romanNumeralLabel(slot.rootOffset, chordType.intervals[1] === 3)` (`theory/notes.ts`) — the chord's roman-numeral position in the progression's own key (e.g. "I", "ii", "bIII"), not its note-by-note interval makeup. This line is identical in Relative and Absolute mode, since it's derived purely from `rootOffset` + chord quality, with no dependence on which concrete root the header has selected. A local `diminishedSuffix(chordType)` appends "°" for fully-diminished chords (`diminished`, `diminished7`) and "ø" for `half-diminished7`, so e.g. a diminished vii chord reads "vii°" — detected via `chordType.intervals[2] === 6` (a diminished 5th at the "5th" stacking position) rather than hardcoded chord ids, the same interval-structure-driven style as the `intervals[1] === 3` minor-quality check; `intervals[3] === 10` (a b7) further distinguishes half- from fully-diminished. Clicking a chip opens a single edit panel below with two `<select>` dropdowns (root interval; chord quality grouped into `<optgroup>`s by `ChordCategory`) that write straight to `state.progression[i]` on every `onChange` — there's no separate pending/draft state, so "Done" only closes the panel, it doesn't commit anything. The edit panel also has "Play Chord" (disabled outside Absolute mode, calls `playChord` on that slot's already-resolved `absoluteChord.notes` — the single-chord-in-isolation counterpart to the panel-level "Play Progression") and "Remove Chord" (lives inside the edit panel rather than as a per-chip button — a per-chip remove button was tried and deliberately reverted), disabled at `MIN_PROGRESSION_SLOTS`; removing the slot currently being edited closes the panel since `editingIndex` no longer points at a valid slot, and removing a slot before the one being edited decrements `editingIndex` so the panel stays pointed at the same logical chord. "Add Chord" appends a default `{ chordId: 'major', rootOffset: 0 }` slot and is disabled at `MAX_PROGRESSION_SLOTS`. "Play Progression" (disabled outside Absolute mode, like every other play button in the app) calls `playChordProgression`. The "Scales Containing This Progression" list reuses `findScalesContainingNotes` directly — no new `relationshipIndex.ts` function was needed, since the union of each resolved chord's pitch classes is already a concrete `PitchClass[]`, the same shape `notesFinder.tsx` already queries with. Loading a preset from `RELATIVE_PROGRESSIONS` (the "Common Progressions" list at the bottom) dispatches `SET_PROGRESSION`, replacing the whole array — it doesn't merge into the existing one. A module-level `KEY_TO_SLOT_INDEX` map plus a `useEffect`-bound `window` `keydown` listener binds slots 1-9 to the `1`-`9` digit keys, slot 10 to `0`, and slots 11/12 to `-`/`+` (both the shifted and unshifted `e.key` variant of each, e.g. `-` and `_`, since which one fires depends on the user's Shift state and keyboard layout) — pressing one plays that positional slot's chord via `playChord`, the same one-chord-in-isolation call the edit panel's "Play Chord" button already makes, just indexed by position instead of by `editingIndex`. Same guards as the scale/chord detail pages' equivalent digit-key shortcut: gated on `isAbsolute`, ignores modifier-held keys, and ignores keydowns targeting a `SELECT`/`INPUT`/`TEXTAREA` so the edit panel's own dropdowns don't fight with it. Bounds-checked against `resolvedSlots.length` since the progression is dynamically sized — a key past the current slot count is a no-op. "Loop Progression" (next to "Play Progression", same Absolute-only disabled gating) toggles a local `isLooping` boolean and gets an `.is-active` class (new `.link-button` modifier in `styles.css`) while on. Looping is a self-rescheduling `useEffect` keyed only on `isLooping` — not on `resolvedSlots`, which is a fresh array every render and would otherwise restart the loop on unrelated re-renders — that calls `playChordProgression` and uses its returned duration (seconds) to `setTimeout` the next repetition; a `loopStateRef` (updated every render, read only inside the timeout callback) keeps the loop reading the *current* progression rather than a stale closure, so editing a chord takes effect on the next cycle the same way "Play Progression" always reflects current state. A second effect calls `setIsLooping(false)` whenever `isAbsolute` goes false, so leaving Absolute mode both stops the audio (the main effect's cleanup clears the pending `setTimeout`) and resets the button's lit state together. `playChordProgression` (`audio/audioEngine.ts`) now returns the total playback duration in seconds (`chords.length * chordDuration`) instead of `void` specifically to support this — the one-shot "Play Progression" call site simply ignores the return value.
- **components/layout/** — `header.tsx`/`appShell.tsx` read/write `AppContext` directly (no intermediate hook wrapper), consistent with tiller's convention of using `useContext` inline rather than a custom hook. There is no `sidebar.tsx` — it was deleted once `ListPage` took over the Scales/Chords browsing role; `appShell.tsx` is just `<Header />` + `<main className="detail-pane">`.

### `src/audio/audioEngine.ts`

A single lazily-created `AudioContext` (created/resumed on first call, respecting browser autoplay policy). `playNote`/`playScaleAscending`/`playChord` schedule `OscillatorNode`+`GainNode` envelopes against `ctx.currentTime`, not `setTimeout`. `playChordProgression(chords: AbsoluteNote[][], rootPitchClass: PitchClass)` extends the same pattern to a whole progression — one `assignOctaves` + simultaneous `playTone` calls per chord, each chord's block offset by `i * chordDuration` from `ctx.currentTime` (the same `ctx.currentTime + i * duration` shape `playScaleAscending` already used per-note, just one level up at chord granularity). Because `assignOctaves` always restarts at the same base octave for every call, a chord whose root pitch class is numerically lower than the progression's root (e.g. header root G, a chord rooted on C) would otherwise be voiced *below* the tonic — both `playChordProgression` and `playChord` guard against this via a shared `anchorAboveRoot(midiNotes, rootMidi)` helper, which shifts a chord up an octave whenever its `assignOctaves` root note (always its lowest, since `assignOctaves`'s output is strictly ascending) lands below `rootMidi = midiNote(4, rootPitchClass)`. `playChord` takes the root as an *optional* second parameter — omitted, it behaves exactly as before (e.g. `chordDetail.tsx`'s "Play Chord" button, which plays a chord that *is* the current root, so there's nothing to anchor against); `progressionBuilder.tsx` passes `progressionRootPc` at both of its single-chord call sites (the digit-key shortcut and the edit panel's "Play Chord" button) so a positionally-played chord matches `playChordProgression`'s behavior instead of sometimes sounding below the "I" chord. This keeps the header's selected root ("I") the lowest-sounding chord, at the cost of the shifted chord sometimes landing a full octave above where its own `assignOctaves` call would otherwise have put it.

`playTone` tracks every `{ oscillator, gain }` pair it creates in a module-level `activeTones` array (removing each entry via the oscillator's `ended` event, so the array doesn't grow unbounded), specifically so `stopAllTones()` can immediately silence anything currently sounding *or scheduled* — needed because clearing a `setTimeout` only stops a JS-level callback from firing again, it does nothing to already-scheduled Web Audio nodes (whose start/stop times were set synchronously up front, e.g. all of one `playChordProgression` cycle's chords). `stopAllTones()` cancels each tone's scheduled gain envelope, ramps it to silence over 30ms (avoiding a click from cutting a mid-ramp note instantly), and stops the oscillator shortly after — `progressionBuilder.tsx`'s loop calls it from the looping effect's cleanup (alongside clearing the pending `setTimeout`) so turning looping off — via the button, leaving Absolute mode, or navigating away — stops audio immediately instead of letting the in-flight cycle finish playing out.

### Styling

`styles.css` is hand-written — no Tailwind, no CSS-in-JS — per `design.md`'s explicit instruction to copy only needed rules from `styles_ref.css` (a ~6300-line reference stylesheet from an unrelated dark-themed marketing site, kept in the repo purely as a style reference, not used directly). Ported from it: the Inter `@font-face` declarations, color palette tokens, dark background tokens, the violet accent (`rgb(139 92 246)`, originally `.card.is-selected`'s ring color), `.link-button`, and the `.checkbox-container` toggle-switch pattern. The app-shell grid, piano, and detail-pane layouts are original — no equivalent existed in the reference file. There is no sidebar column anymore; `.app-shell` is a single-column grid (`'header'` / `'main'` areas only).

`.note-picker` (the Notes view's toggle-button row, `notesFinder.tsx`) deliberately does **not** ride along in the `.scale-detail`/`.chord-detail`/`.list-group` shared chip-selector list even though it looks similar — those three style `<li><a>` navigation chips, but `.note-picker` styles stateful `<button>` toggles with an `.is-selected` variant (using `--color-accent`, same token as the piano's `.is-active`/`.is-root` keys and `.checkbox-container.is-enabled`), which is different enough behavior that it gets its own small rule block instead of a 4th selector joining that group.

The app renders inside a 1200px "gutter": `.header-inner` and `.detail-pane` both use `width: 100%; max-width: 1200px; margin: 0 auto;` to center their content, while `.header` itself has no such cap so its background spans the full viewport edge-to-edge — only its *contents* (wrapped in `.header-inner`) are confined to the gutter. **The explicit `width: 100%` is load-bearing, not redundant with `max-width`** — relying on `max-width` + `margin: 0 auto` alone let `.detail-pane` shrink-wrap to its content's natural width instead of stretching to fill the gutter on pages with narrower content (the Chords list, whose widest row is narrower than the Scales list's), which silently broke the gutter alignment on exactly one of the two list pages and nowhere else. Don't drop `width: 100%` when touching either of these rules.

`.header` is `position: sticky; top: 0`, and the *document* (`html`) is the one scrolling element — not an inner `overflow-y: auto` pane on `.detail-pane` like an earlier version of this layout used. That earlier approach hid `.detail-pane`'s own scrollbar (`scrollbar-width: none` / `-ms-overflow-style: none` / `::-webkit-scrollbar { display: none }`), but a hidden scrollbar on one element can still reserve invisible layout width inconsistently across browsers (particularly Windows Chrome's "classic" reserved-space scrollbars), which the sibling `.header` never loses — throwing the two out of alignment in ways that don't reproduce in headless Chromium. Making `html` the sole scroll owner (with the same scrollbar-hiding trio now applied there instead) means both the header and the content share one width computation and can't drift apart. If page-level scrolling is ever removed in favor of an internal scroll pane again, expect this class of bug to come back.

### Build/tooling gotchas

- `tsconfig.app.json` has `verbatimModuleSyntax: true` and `erasableSyntaxOnly: true`. Every type-only import must use `import type` (or an inline `type` per specifier when mixing value + type imports from the same module), and TypeScript `enum` syntax will fail the build (use the `as const` pattern instead).
- **`npx tsc --noEmit` from the repo root does not exercise these strict settings** — it doesn't go through the project-reference build. Only `tsc -b` (i.e. `npm run build`) does. Always verify with `npm run build`, not a bare `tsc` invocation, before considering a change verified.
- The project is pinned to **Vite 6** + `@vitejs/plugin-react` 4, not Vite 8. Vite 8's default bundler (Rolldown) requires a native binding package that fails to install on Node 20.18.0 (below Rolldown's required 20.19+). Don't upgrade Vite past 6.x without addressing this first.
- `tsx` is a dev dependency for ad hoc scratch verification scripts only (e.g. `npx tsx scratch-check.ts`) — it is not a test runner and no test suite exists by design.
